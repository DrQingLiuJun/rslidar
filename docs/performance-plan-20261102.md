# 三路广场激光雷达性能分析与部署方案

检查日期：2026-11-02。服务器172.16.4.81，工作区`/home/user/carla-projects/rslidar_ws`。

建议目标架构：**三路点云按时间和外参统一到广场坐标，一套面向合并场景训练的轻量单阶段检测器，一套广场跟踪，CPU上与相机目标融合，GPU为检测与CARLA分别留预算。** 首个候选选PointPillars及经验证的FP16/TensorRT部署路线；若小目标召回不达标，再比较轻量CenterPoint等候选。现有三套PV-RCNN保留为精度和时延基线。

这是根据当前现场的工程优先方案，不是未经训练和实测就认定某网络在本场景绝对最优。本次没有更换权重、修改生产配置、停止服务或启动第四套GPU推理。完成的是现场观测、源码/权重/配置审查，以及离线CPU点云统计；统一新模型尚未实测FPS及精度。

## 1. 现场确认的事实

- GPU报告RTX4090、约48GiB显存，使用约11GiB、GPU利用率100%。显存容量和算力/传输/调度效率是不同维度，显存余量不能保证帧率。
- 当前已有三个PV-RCNN计算进程、CARLA和RViz。CARLA进程参数为Epic、1600×900，不能将此时全部GPU负载归因于雷达。
- 当前总体融合服务为停止后的failed状态，退出码130；日志显示SIGINT停止，不据此判断为GPU崩溃。本次没有擅自重启该服务。
- CARLA只读采样12秒，世界帧推进约29.1Hz，但采样到的tick间隔P95约98.4ms，存在约0.1秒的尾延迟。此指标不是浏览器最终展示帧率，也不能代替完整渲染耗时剖析。
- 三路点云原先已验证10Hz、队列深度1。10Hz首先是当前输入发布节奏，不应把它直接理解为GPU只能处理10帧。
- 当前5分钟检测日志抽样：第一路中位320.15ms/P95 340.15ms，第二路321.70/337.06ms，第三路314.95/334.20ms；观测到约2.3–2.5秒尖峰。这是日志抽样的callback墙钟耗时，包含预处理、GPU排队/执行及发布，不是逐层CUDA耗时，也不是真正从采样到展示的端到端时延。

NVIDIA对GPU利用率的定义是采样期间至少有kernel执行的时间比例；100%不等于所有计算单元/Tensor Core都达到峰值。[NVIDIA说明](https://docs.nvidia.com/deploy/nvidia-smi/)

## 2. 三份模型确实不同，当前配置偏重

| 项目 | .36 / 第一路 | .39 / 第二路 | .41 / 第三路 |
|---|---:|---:|---:|
| 模型 | PV-RCNN | PV-RCNN | PV-RCNN |
| 输入体素m | 0.1×0.1×0.2 | 0.05×0.05×0.4 | 0.1×0.1×0.2 |
| XYZ网格 | 944×800×45 | 992×2320×40 | 672×496×73 |
| BEV格子数 | 755,200 | 2,301,440 | 333,312 |
| 关键点 | 4096 | 4096 | 4096 |
| 二阶段测试候选上限 | 300 | 300 | 300 |
| 每候选RoI网格 | 6×6×6 | 6×6×6 | 6×6×6 |

第二路BEV格子约为第一路3.05倍；这只是配置成本线索，不表示实测GPU耗时必然3倍。稀疏卷积有效体素数、关键点聚合、RoI池化、CPU准备和三个CUDA上下文争用都需要分别测量。

三份checkpoint SHA256不同，第一/第二路319个状态张量形状相同但没有逐项完全相等的张量；第三路有3个状态张量形状也不同。不能简单共用现有一份权重、平均权重或将三份现成模型做成一个batch而保持原行为。

状态张量数据每份约50MiB，而每个计算进程当前约占2.5GiB GPU内存。其余包含中间特征、缓存/工作区和上下文等；具体比例需要内存剖析。故只省掉两份权重张量不会自动省掉三分之二显存，更不会省掉三分之二计算。

PV-RCNN本身结合体素卷积、关键点特征聚合和RoI网格池化，当前三路各自重复执行这些阶段。[原论文](https://arxiv.org/abs/1912.13192)

## 3. 合并点云的CPU统计：会有收益机会，但不是三变一就快3倍

采集了每路4个真实点云样本，不执行额外GPU推理。第一组在各自原检测ROI内共有188,225个有限点，三路约31万原始点中还含有无效回波及ROI外点。样本只用于空间工作量统计，没有严格同步到同一激光发射时刻。

按现有三维外参变换，各ROI联合包围框约152×124米。体素占用统计如下，使用全部有效ROI点，而不是生产随机采样后的点：

| 统一体素m | 分路占用体素之和 | 合并占用体素 | 重复占用减少 | 联合包围框BEV格子数 |
|---|---:|---:|---:|---:|
| 0.05×0.05×0.4 | 123,614 | 122,460 | 0.93% | 7,541,680 |
| 0.1×0.1×0.2 | 102,988 | 101,434 | 1.51% | 1,886,040 |
| 0.16×0.16×0.25 | 79,351 | 76,953 | 3.02% | 737,025 |
| 0.2×0.2×0.25 | 68,880 | 66,327 | 3.71% | 471,820 |

这些是样本的几何占用，不是神经网络时间、显存或精度测试。不同角度的激光即使打在同一物体上，也经常落在不同点和不同体素；标定残差、扫描相位也会影响占用。因此不能期待仅靠去重把18.8万点变成约6万点。

真正可节省的是统一特征提取、关键点采样、检测头和NMS等重复工作，以及多个CUDA上下文/重复工作区。另一方面，统一覆盖范围会增大，活跃体素和背景候选仍可能很多。如果沿用第二路5厘米分辨率扩成整个场景，BEV达到754万格，比当前三路BEV之和约339万格还大，存在变慢的风险。

统一0.16米的BEV约74万格只是一个值得验证的工作量起点；分辨率变粗可能伤害远处行人和骑行者，必须通过重训及标注集验证，不能只改旧模型voxel_size就上线。首先保留既有覆盖作为基准；裁掉非验收区域必须明确说明覆盖变化，不能用丢失覆盖来制造帧率提升。

另外，当前代码先静态过滤、随机截到8万点，再由数据处理器裁ROI；随机预算会被NaN和ROI外点占用。按同样顺序CPU模拟，第一路进入ROI约4.7万点、第二路约3.85万点、第三路约4.5–5.1万点。建议有限值与ROI筛选先行，再做有配额的分层采样。但若仍使用8万上限，该调整也可能增加实际进入网络的有效点，不能把它单独宣传为必然提速。

## 4. 几种架构的区别

| 方案 | 计算次数/场景周期 | 精度/训练前提 | 判断 |
|---|---|---|---|
| 三进程、三套PV-RCNN | 3次 | 保留现有分路模型 | 当前基线，需增加资源预算控制 |
| 单进程轮询三套现有权重 | 3次 | 可沿用分路坐标和模型 | 适合短期改善调度；不会自动消除三次计算 |
| 一套共享权重，分别处理三路 | 3次或一次batch=3 | 需统一输入规范和多设备训练，第三路结构也需处理 | 权重复用有价值，但不是一次场景推理 |
| 合并点云，直接塞进某个现有PV-RCNN | 表面1次 | 输入分布、坐标、范围、密度都变了 | 不作为可靠部署方案 |
| 同步合并，一套场景级轻量检测 | 1次 | 合并点云与统一标注训练，重新验证小目标 | 推荐的目标架构 |

吞吐改善需要满足：合并前处理耗时＋统一推理耗时＋后处理耗时，低于原三路占用的相应资源预算。不能把三路并发各约330ms直接相加为990ms，再据此宣布新模型可快三倍。

## 5. 推荐落地架构

```text
三路10Hz原始点云
  → 时间缓存与对齐、三维外参变换（CPU）
  → 统一广场局部坐标、有效ROI、体素/分层采样
  → 单GPU进程、一个统一轻量模型、一次场景检测
  → 广场目标跟踪与去重（CPU，标明新观测与预测）
  → 与边缘机相机结果进行总体融合（CPU）
  → CARLA桥接与限预算渲染（GPU）
```

模型首个工程候选为PointPillars。它将点云编码为柱状特征后使用2D卷积，适合优先验证轻量部署；官方也提供相应TensorRT部署路线。现有OpenPCDet PV-RCNN checkpoint不能直接变成PointPillars或TAO引擎，转换链路与算子支持需要单独核对。[PointPillars原论文](https://arxiv.org/abs/1812.05784)、[NVIDIA部署文档](https://docs.nvidia.com/tao/tao-toolkit/latest/text/cv_finetuning/pytorch/point_cloud/pointpillars.html)

不得把论文KITTI帧率搬成该152×124米广场的承诺。若PointPillars在行人/骑行者远距离召回上不能达到验收标准，比较轻量CenterPoint等候选；模型选择以同场景标注精度和整机时延共同决定。

实施条件：

- 每台只保留少量最新帧，按实际时间戳选最近的三帧；30–50ms作为待现场验证的初始对齐容差，不无限等待缺路。当前主机接收时间戳不等于严格硬件同步，需检查DIFOP/PTP/GPS时钟及帧内采样时间。
- 合并的是同一时间窗口，不连续叠加很多旧帧；动态目标在长时间窗内会拖影，静态标定不能消除该问题。
- 使用居中的广场坐标，而不是直接将庞大地理数值作为模型输入；高度、yaw、强度规范和80/32线密度分布应在训练与部署时一致。
- 使用统一3D标注，每个物理目标在合并帧中只有一个真值框。原三路标注转换后需要对时、去重和核对，原预测不能直接当真值。
- 训练加入单路/双路缺失情况；部署一台掉线时输出健康状态，按有效传感器退化，不能一直等齐三路或重复使用旧帧。
- 采样保留远处和小目标，不让近处地面/树冠密度耗尽预算。是否移除地面应与训练保持一致，不能把目标底部等点盲目删除。
- 一个推理worker持有模型和工作区，前后处理与推理尽量解耦；队列保持有界。FP16、候选数、体素和点预算分别验证，不承诺加一个开关就能翻倍提速。

如果暂时无法制作可靠的同步合并标注，可先训练覆盖三个设备的共享轻量模型、分路推理后晚融合；该路线更易复用分路标注。只要它已满足整机预算和精度，就不必为了形式上的“合并”额外引入高风险改造。

## 6. CARLA与显示也必须有资源预算

当前CARLA Epic 1600×900与推理竞争GPU。首先评估720p、20–30FPS封顶、阴影和后处理的定向优化，避免同时长期运行多个全分辨率调试视图。RViz生产时可关闭，或降低显示分辨率/显示点数，不改变检测输入。

不能简单把CARLA切Low后就认为部署完成：官方Low会将绘制距离设为50米，可能影响整个广场的远端actor显示，应检查现场版本和远端可见性后再采用。Off-screen仍会渲染；No-rendering会让GPU相机没有图像，不适合最终看CARLA画面的目标。[CARLA官方说明](https://carla.readthedocs.io/en/latest/adv_rendering_options/)

现有总体融合主要为C++/Eigen CPU计算，并非又跑三套GPU网络；接入后GPU新增负担主要还取决于CARLA actor与相机渲染。不能将融合的CPU代价与PV-RCNN的GPU代价混为一谈，也不能认为现在未开启融合就没有CARLA负载。

轨迹可以用20–30Hz的CPU预测和桥接插值改善连续性，但真实新检测频率仍为5–10Hz；不可把插值频率宣称为检测帧率。

## 7. 接入总体融合的关键一致性问题

现场另发现两个项目的`map`原点不同：

- 雷达：纬度34.5878275、经度113.6800472。
- 总体融合：纬度34.5878213、经度113.6790488。
- 两者原点约相差东向91.498米、北向0.690米。

两个坐标系即使都命名map也不能直接接。必须通过统一参考点/明确坐标变换接入；现有雷达内部相互对齐，并不意味着已对齐服务端总体map。不要通过修改CARLA actor位置去抵消这个源头差异。

场景级雷达作为一个有来源说明的观测分支接入，不能把合并后的同一检测再复制成三份独立观测，造成置信度重复累积。输出应是结构化目标数据：采样时间、坐标系、类别、分数、位置/朝向/尺寸、协方差或质量、来源传感器、健康状态。MarkerArray与经纬度文字是调试显示，不能作为可靠融合协议。

现有雷达模型仅有Vehicle/Pedestrian/Cyclist；要对接总体融合的car/truck等类别，需定义语义映射或补充类别训练。还需显式增加雷达分支的来源和广场区域支持，不套用道路相机的专用位置修正、出生区域或历史轨迹规则。

## 8. 实施次序及验收门槛

1. 保留当前三模型作基线，建立同步输入和整机性能记录，剖析预处理、GPU等待/计算、后处理、ROS、融合、桥接及最终图像年龄。下一步受控GPU基准应在维护窗口执行，避免现场加第四个推理进程后把争用误当性能结果。
2. 先限制显示预算、设计一个推理调度入口，保留有限值/ROI/采样质量与故障状态。短期调度改善不等于模型计算量减少，不承诺现有PV-RCNN立刻达到10Hz。
3. 制作统一场景训练/验证数据；候选先做PointPillars，保留同覆盖、同验证集的三PV-RCNN基线。验证FP32→FP16→部署引擎的逐步精度变化。
4. 达标后替换为场景级检测分支，再接入总体CPU融合与CARLA，完整联调。

建议第一阶段场景检测目标5Hz，最终争取10Hz；它们是待验证工程目标，不是当前模型已测性能。以10Hz周期为例，可先将感知GPU工作预算设为约60ms，给渲染等留余量；必须通过实际时间线验证，不能等价换算为nvidia-smi百分比。

建议联合验收：

- 全覆盖条件下场景检测≥5Hz，目标10Hz；关注P95/P99时延与最大中断，不只看平均FPS。
- 端到端采样到融合输出P95暂定≤150ms、P99≤250ms，并明确最终画面额外传输/编码延迟。
- CARLA目标显示≥20Hz，目标30Hz，长时间没有持续卡死；保持全部验收区域的可见性。
- 固定3D/BEV评价口径，对行人、骑行者、车辆按距离统计AP、精确率和召回；远处小目标单独验收。没有人工标注就不能用“检测框变少/看着顺滑”判断精度改善。
- 单路断流、延迟和掉帧可退化；同一物理目标不重复计数；不同map原点、重复预测和来源置信度不会污染总体融合。
- 至少连续30分钟、较密目标场景下测试，GPU显存稳定、接收无持续丢包。资源预算通过时延和全栈稳定性验收，不能单独以GPU利用率是否低于某个百分比验收。
